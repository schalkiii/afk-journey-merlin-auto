# GUI 结构与视觉规范

本文说明主界面（`Goldenhandmaidens.GameBotGUI`）的布局规则、配色约定、「定时生效」的
提示链路，以及**为什么每个子进程都要隐藏控制台**。末尾给出「是否该换更现代的 GUI 框架」
的评估结论与迁移触发条件。

## 一屏三段式

窗口从下到上分三段，只有中间那段会随窗口缩放变化：

```text
┌──────────────────────────────────────────────────────────────┐
│ 控制栏（固定高）                                              │
│   主操作：开始运行(F8) / 启动游戏并运行 · 右：当前任务 检查更新 版本│
│   运行选项：5 个勾选项                                        │
│   定时：游戏等待 / 定时开始 / 设定定时 / 短状态                │
├──────────────────────────────────────────────────────────────┤
│ 定时横幅（未设定定时时整条隐藏，不占高度）                      │
├──────────────────────────────────────────────────────────────┤
│ 可拖动分栏                                                    │
│   上：功能列表（可滚动） │ 配置面板（可滚动）                   │
│   ── 拖动分隔条可调整上下比例 ──                               │
│   下：运行日志（自身滚动）                                     │
└──────────────────────────────────────────────────────────────┘
```

要点：

- **控制栏永远固定高、永远完整可见**。它是操作的唯一入口，任何缩放下都不允许被裁。
- **主体上下用 `ttk.PanedWindow`**：窗口变矮时由用户决定把高度让给配置还是日志；
  两半内部各自滚动，不存在「某个面板永远看不到」。
- 三个分区都是白卡片（`LabelFrame`），浅灰页面底色只在大块留白处露出。

## 缩放行为（用户反馈的「拖小就看不到控件」）

老版本把选项、定时、状态全塞进同一个 `pack(side=LEFT)` 流里。**pack 不折行**，窗口一窄
右侧的「设定定时」就被裁到可视区外——这正是当时看到的症状。现在的三条规则：

| 规则 | 实现 | 保证 |
| --- | --- | --- |
| 变窄时整组下移 | `_FlowRow`：按 `winfo_reqwidth` 累加，超宽就换行（`<Configure>` 里重排） | 任何宽度下控件都在，不会被裁 |
| 变矮时内容可滚 | 配置面板与功能列表都是 `Canvas + Scrollbar` | 参数再多也能滚到 |
| 上下分配可调 | `PanedWindow(weight=3 / 2)`，可拖动分隔条 | 日志挤不走配置，配置也挤不走日志 |

`_FlowRow` 只在**宽度变化 ≥4px** 时重排：折行会改变自身请求高度，跟着高度回调再排会自激。
另外 `add()` 会先把控件按一行放好，窗口首帧（或测试里 withdraw 的根）收不到 `<Configure>`
时也不会出现「控件已创建但从未布局」的空档。

最小窗口 880×560：这是「三行控制栏各自最宽项加起来仍放得下」的实测值（老版本 1024×640
仍会把定时块挤出去）。

## 视觉规范

统一用 `clam` 主题。**vista 主题会忽略 ttk 的 `background` / `bordercolor`**，只能调字体和
padding，界面永远是系统灰；clam 能吃配色，代价是要把默认样式铺一遍（见 `_setup_theme`）。

| 用途 | 色值 | 说明 |
| --- | --- | --- |
| 页面底色 | `#EDF1F6` | 只在留白处露出 |
| 卡片 | `#FFFFFF` | 所有分区的底色，ttk 默认背景也设成它 |
| 描边 | `#D6DDE6` | 卡片与输入框边框 |
| 正文 / 次要文字 | `#1F2933` / `#6B7A8C` | |
| 强调色 | `#2563EB` | 主按钮、选中行、勾选方块 |
| 危险色 | `#B91C1C` | 运行中的「停止运行 (F9)」 |
| 定时横幅 | 底 `#FFF4CE`、字 `#5C4400`、边 `#E0A800` | 与蓝灰主色刻意区分 |

按钮分三档，语义固定：

- `Accent.TButton`：主操作（开始运行），运行中变成 `Danger.TButton`（停止运行）。
- `Outline.TButton`：白底蓝边的次级入口（启动游戏并运行）。
- `TButton`：其余普通按钮。

两个自定义控件值得单独说明：

- **`_ToggleBox`（自绘勾选框）**：clam 把 ttk 的「已勾选」渲染成一个 **✗**（放大 6 倍实测
  确认），看起来像「禁用/出错」；本机 Tk 8.6 的经典 `tk.Checkbutton` 又只填 `selectcolor`、
  不画对勾。于是用 Canvas 画 16×16 方框 + 折线对勾，尺寸与配色完全可控，也不依赖字体里
  有没有 ☑ 这类符号。所有勾选项统一走 `_checkbutton()`。
- **单选项**：ttk 的 clam 默认「未选」也是一个蓝点，和「选中」分不清；用
  `App.TRadiobutton` 把指示器底改白、圆点用强调蓝。

## 定时生效的提示链路

「以为没设定时 → 到点游戏被莫名拉起」的代价很高，所以提示做成三处冗余、一个出口：

1. **常驻横幅**：琥珀底 + 深棕加粗字，写明「每天 HH:MM 自动启动游戏并运行 · 剩余 hh:mm:ss
   （下次 日期 时间）」，右侧带「取消定时」。未设定时整条隐藏，不占高度。
2. **标题栏角标**：`梅林初号机 · ⏰ 定时 08:00`（运行中再加 `▶ 任务名`）。窗口被游戏盖住、
   只剩任务栏时，这是唯一还看得见的地方。
3. **设定瞬间脉冲**：横幅亮暗交替 6 拍（约 1 秒）后停在常态色，作为「确实注册上了」的确认。

三处都由 `_set_schedule_status(text, banner=...)` 一个出口刷新。**倒计时只放横幅**：它每秒
都在变，塞进行内标签会把控制栏反复挤到折行。

另外修掉一处语义漏洞：定时到点时若脚本正在运行，旧实现跳过本轮后**直接返回**，等于「每天
循环」在第一次撞车后静默失效到下次重启；现在会重新排上明天的定时。

## 为什么子进程一律隐藏控制台

成品是 GUI 子系统（`console=False`，实测 PE `Subsystem=2`），进程本身**没有控制台**。此时
`CreateProcess` 启动任何控制台子程序，Windows 都必须给它新建一个控制台窗口——用户看到的
就是每次启动/关闭工具时一闪的黑色 cmd 框。实测触发点：

- 启动游戏前读桌面 `.lnk` 目标：`powershell`；
- 探测/回收点击注入器：`tasklist` / `taskkill`；
- 安装更新：`cmd /c update.bat`。

结论：改 spec 没用，只能在创建子进程时带上隐藏标志。全仓统一走 `proc_util.py`：

```python
run_hidden(["tasklist", "/NH"], capture_output=True)   # 等价 subprocess.run + 隐藏控制台
popen_hidden([ahk_exe, script, work_dir])              # 等价 subprocess.Popen + 隐藏控制台
```

`CREATE_NO_WINDOW` 让子进程完全不带控制台，`STARTF_USESHOWWINDOW + SW_HIDE` 是双保险。
`tests/test_20261114_hidden_console.py` 用 AST 扫描守住这条规则：任何文件（`proc_util.py`
除外）出现裸 `subprocess.run/Popen` 即失败。

实测数据（2026-11-14，无控制台的 `pythonw` 里做 A/B，统计「新出现的可见控制台窗口」）：

| 子程序 | 裸调 `subprocess.run` | 走 `run_hidden` |
| --- | --- | --- |
| `tasklist` | 1 | 0 |
| `cmd /c` | 1 | 0 |
| 成品 `goldenhandmaidens.exe` 启动→关闭全程 | — | 0 |

注意 `stdout=PIPE` 会让 conhost 还没画出窗口子进程就退了，容易漏测——对照组必须让子进程
继承句柄（不重定向）才稳定复现黑框。

## GUI 框架评估

结论：**现阶段继续用 Tkinter**，不迁移。评估维度如下。

| 方案 | 体积代价 | 迁移成本 | 主要收益 | 主要风险 |
| --- | --- | --- | --- | --- |
| Tkinter（现状） | 0（成品 92.9 MB 主要是 opencv/numpy） | — | 零依赖、打包稳定、线程/热键模型已验证 | 观感朴素；ttk 主题能力有限，个别控件要自绘 |
| PySide6 (Qt6) | +60~80 MB | 全量重写界面（约 900 行 UI + 事件绑定） | 现代控件、样式表、高 DPI 与多语言成熟 | 大包体；Qt 事件循环与现有「主线程 Tk + 后台线程」模型要重新对齐 |
| PyQt6 | 同上 | 同上 | 同上 | GPL / 商业授权，分发受限 |
| Dear PyGui | +10 MB 左右 | 全量重写，且要自己做文本日志控件 | 即时模式、GPU 绘制、帧率高 | 中文输入法/字体细节差；日志这类富文本控件要自造 |
| pywebview + 本地 HTML | 依赖系统 WebView2 | 界面重写为前端，另加一层桥 | 观感最现代，前端生态齐全 | 多一层前后端通信；高频日志需节流；调试链路变长 |

判断依据：

1. **UI 规模小**（单窗口、约 900 行），收益上限有限；换框架等于把已实机验证过的交互
   （拖拽排序、热键、状态色、分栏）全部重做一遍，回归成本远大于观感提升。
2. **体积不是瓶颈也换不来什么**：成品 92.9 MB 的大头是图像处理依赖，Qt 只能再加 60~80 MB。
3. 现在的痛点（勾选框观感、主题不可控）已经用**自绘控件 + clam 配色**解决，属于一次性成本。

迁移触发条件（满足任一条再考虑 PySide6）：

- 需要多页面 / 图表化统计 / 主题切换 / 多语言等真正的「应用级」界面；
- UI 代码超过约 3000 行，Tkinter 的组织能力开始拖累维护；
- 出现必须依赖 Qt 的能力（复杂表格、富文本编辑、图表库）。

真要迁移时，只重写 UI 层：业务入口已经是「回调 + `ScriptConfig` 列表 + `self.log()`」的形态，
`run_scripts_thread` / 各 `flow_*` 模块不需要动。

## 已知取舍

- 滚动条常显（不做自动隐藏）：内容是否可滚一眼可见，避免「以为到底了」。
- 滚轮在根窗口统一监听一次，按指针位置派发给最近的滚动容器（`_on_mousewheel`）。嵌套滚动区
  （配置面板里的仓库英雄列表）各自 `bind_all` 会互相顶掉绑定，这是唯一稳定的做法。
- 功能列表的启用勾选框不带 `width`：经典 `Checkbutton` 的 `width` 是文本宽度，留空时会把
  指示器挤出边界（实测未勾选态只剩一个「└」角）。自绘后已无此问题，但规则保留说明。
